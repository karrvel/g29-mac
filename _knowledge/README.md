# _knowledge — the g29-mac local knowledge base

> This file + your project-root `CLAUDE.md` are **Karpathy layer 3 — the schema**.

Plain-markdown, git-trackable, Obsidian-compatible knowledge, distilled from the codebase and from
past AI-agent sessions. Design = **Karpathy's "LLM wiki"** (compile once, don't re-derive) +
**MemGPT/Letta two-tier memory** (tiny always-loaded core + on-demand vault). Deliberately **shallow
and plain-markdown — no vector/spatial RAG** (unnecessary below ~150–200 pages; see
`../research/plain-markdown-vs-vector-rag.md`).

## Two-tier memory (how a future agent should use this)
1. **Core (always-loaded):** Claude Code project memory `MEMORY.md` — the index that auto-loads.
   Keep it tiny: one line per fact, pointers only. Auto-loads for sessions at the memory-keyed root.
2. **Archival (on-demand):** this vault. Read [[INDEX]] first, then open only the pages you need.

The project-root `CLAUDE.md` is the quick-boot orientation + **LIVE sync blocks**; it is discovered
hierarchically (loads from inside subdirs too), so it's the reliable carrier of the LIVE tier for
per-repo work. `MEMORY.md` and the `CLAUDE.md` blocks are generated by `kb-sync.py` — do not
hand-edit them. Both halves are gated on `claude` being listed in `KB_PLATFORMS`; if there's no
project-root `CLAUDE.md` at all, kb-sync warns and continues, and the LIVE blocks stay unwired until
you create it with the two marker pairs.

## Platform files (generated — do not hand-edit)
`kb-sync.py` generates context files for multiple agent platforms from the same vault shards:

| File | Platform | Notes |
|---|---|---|
| `AGENTS.md` | Codex CLI, Antigravity ≥ v1.20.3 | Cross-tool standard |
| `GEMINI.md` | Google Antigravity | Takes priority over `AGENTS.md` within Antigravity |
| `.cursor/rules/kb-context.mdc` | Cursor | `alwaysApply: true` frontmatter |
| `~/.claude/.../MEMORY.md` | Claude Code | Lives outside repo; never committed |

**Collision guard.** Those three project-root files (`AGENTS.md`, `GEMINI.md`,
`.cursor/rules/kb-context.mdc`) are *not* generated unconditionally: if one already exists and
kb-sync didn't generate it, kb-sync warns, skips that file, and continues (exit 0). Rename or move
your file, or drop that platform from `KB_PLATFORMS` — never paste the generated block into your own
file, or kb-sync will treat the file as its own and overwrite it on the next run. `MEMORY.md`,
`INDEX.md` and the MOCs are **not** guarded: kb-sync always rewrites them.

Control which files are generated with `KB_PLATFORMS` (comma-separated; default
`claude,codex,gemini,cursor`; surrounding whitespace is tolerated). It is read from the environment
of the kb-sync run, so it must be exported — e.g.
`KB_PLATFORMS=claude,gemini python3 _meta/kb-sync.py`, or `export`ed in your shell profile; putting
it in `.githooks/kb.env` only affects hook-triggered runs. `claude` covers both `MEMORY.md` **and**
the `CLAUDE.md` LIVE blocks.
Commit `AGENTS.md`, `GEMINI.md`, and `.cursor/rules/kb-context.mdc` to the repo.

**Orphan guard.** Removing `codex`, `gemini` or `cursor` from `KB_PLATFORMS` stops kb-sync *writing*
that project-root file; it does not remove a file already written. The leftover stays on disk — and,
committed as advised above, keeps feeding every agent the LIVE security findings and open work frozen
as of the last run. kb-sync therefore warns about such a file on a normal run and under `--check`,
naming it and the platform, until you **delete the file** or **put the platform back in
`KB_PLATFORMS`**. It never deletes or edits the file itself (your git may track it), and it says
nothing about a same-named file *you* wrote — that one is the collision case above. `MEMORY.md` and
`CLAUDE.md` are out of scope, so dropping `claude` is not reported. An orphan is a warning, not an
error: a normal run still exits 0.

## Frontmatter schema (every shard)
```yaml
---
name: <short-kebab-case-slug>        # unique; used for [[links]]
type: gotcha|decision|security|task|repo|architecture|reference
title: <one-line human title>
area: <backend|frontend|mobile|infra|cross|…>
tags: [<free tags>]
status: active|superseded|resolved
updated: YYYY-MM-DD
volatility: durable|decays-with-code|one-shot
provenance: <where this came from — session date/id, doc, or code path>
# optional fields:
verify: YYYY-MM-DD          # date of last human re-verification; planned for kb-staleness reporting
live_summary: <short phrase> # shown in LIVE blocks instead of title: (max ~80 chars)
---
```
> **Provenance tip:** for `decays-with-code` shards, prefer a **git-anchored** provenance —
> `verified vs main@<short-sha> YYYY-MM-DD` — so a future reader can tell exactly which code state
> the claim was checked against. It's the strongest freshness signal a shard can carry.

**Browse it as a database:** `knowledge-map.base` ships with this scaffold — open the vault in
Obsidian (1.7+, Bases core plugin) for filtered table views per `type`. Plain markdown underneath;
no plugin needed to read/grep/diff.

## Volatility tags (read before trusting a shard)
- **durable** — true regardless of code state. Trust it.
- **decays-with-code** ⚠️ — accurate only as of `updated:`; **re-verify against code before acting.**
- **one-shot** — a closed/resolved record kept for history.

### Tagging a security shard so it lands in the right place
`status` and `volatility` answer different questions, and the always-loaded
**🔴 LIVE — open security findings** block needs **both**:

| Shard | `status` | `volatility` | Appears in the LIVE block? |
|---|---|---|---|
| An open finding about this code | `active` | `decays-with-code` | **yes** — that's what LIVE is for |
| A finding you've fixed | `resolved` | `decays-with-code` | no |
| A standing rule ("never commit secrets") | `active` | `durable` | no — it's policy, not a finding |

Tag a real finding `durable` and it stays out of the LIVE tier; leave a fixed one `active` and
agents keep being told it's open. The `security/` MOC groups by volatility instead, so durable
rules and findings are both browsable there.

## Maintenance discipline (the part everyone skips)
- **Append, don't rewrite.** New event → a line in [[log]]. New trap → a shard in `gotchas/`.
- **Write the *why*.** Decisions die with the context window unless captured in `decisions/`.
- **Mark superseded, don't silently delete.** Add `status: superseded` + a pointer.
- **Tag volatility + provenance on every shard.** Weight recent over old.
- **Verify load-bearing facts against code.** Architecture/repo claims must match the code.
- **Keep the core tiny.** Cap the always-loaded tier (~30 items); push detail into the vault.
- **Regenerate after edits:** `python3 _meta/kb-sync.py` from the project root (rebuilds MOCs +
  INDEX + both memory tiers). `_meta/` is gitignored, so it doesn't arrive with a clone — every
  contributor installs the kit scripts (and enables the commit gate) once, or their ungated commits
  can land an invalid shard that blocks everyone else.
- **Never store secrets here.** Tokens/keys → secret manager, never markdown.
