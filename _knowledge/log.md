## [2026-09-01] build | G29 force feedback made to work on Apple Silicon, two of three sims installed
Proved Apple's ForceFeedback stack refuses the G29 (`FFIsForceFeedback` -> 0x80000003, no PID usage page) and that SDL2 and Wine inherit that failure. Reached the motor instead with raw Logitech HID output reports; `lgwheel --verify` measured the wheel driving itself across 100% of its travel. Built `sdl2-lg4ff-shim` to substitute Wine's SDL2 so Windows sims get a real DirectInput FFB device — verified end to end, Live for Speed emits a constant-force effect and Speed Dreams emits constant + periodic. Installed Live for Speed and Speed Dreams 2.4.2 into a new Whisky bottle ("Sim Racing"); RaceRoom staged but blocked on an interactive Steam login. Hard-won details: 7-byte commands must be padded to the interface's 16-byte report or the endpoint STALLs, and the FFB interface is the joystick one (usage 01:04), not the vendor-defined one.

## [2026-09-02] fix | Steam bootstrap unblocked; G29 pedal mis-binding diagnosed
Steam in the bottle was failing fatally with "needs to be online to update" while the host had working internet. Cause was Wine's WinHTTP running WPAD proxy auto-detection across all 26 network interfaces on this machine (8 VPN tunnels + Docker/UTM/VirtualBox bridges), stalling the manifest request until the updater gave up. Disabled proxy autodetect via the `WinHttpSettings` registry blob; Steam then self-updated to a full 1.6 GB client and now reaches the login screen. Separately, measured the G29's axes: only four exist, and `Z`/`Rz` rest at full scale while `Y` rests near zero — which is why LFS auto-bound the clutch (`Y`) as the throttle and ignored the real pedals. Added `identify-pedals.sh` and `lgwheel --axes` to measure this directly. Fix is in-game re-calibration, not editing the binary `.csf`.

## [2026-09-02] fix | Pedals and steering working in LFS — the FFB change had broken input
Enabling Wine's SDL backend for force feedback also made winebus emit a wheel descriptor with Simulation Controls axes (Steering 0xC8 / Accelerator 0xC4 / Brake 0xC5 / Clutch 0xC6). LFS only binds Generic Desktop axes, so its pedals became unbindable — an input regression caused by the FFB fix, which read as two unrelated faults. Fixed by overriding `SDL_JoystickGetType` in the shim to report the wheel as a generic joystick; dinput then exposes GUID_X/Y/Z/Rz while `SDL_JoystickIsHaptic` still claims haptics, so both work. Confirmed by the user: steering and all three pedals now correct. Added `reset-bottle.sh` (wedged wineserver) and `reset-lfs-controls.sh` (stale binary .csf).

## [2026-09-02] perf | LFS lag fixed: DXVK + trimmed quality, ~39-58 fps spiky -> 100 fps at 8.5-11.5 ms
Whisky creates bottles with DXVK disabled, so LFS was running on wined3d's own Vulkan backend — slow and, worse, badly paced. CPU sat at ~12% while the frame rate was low, which ruled out Rosetta/translation and pointed at presentation. Installed DXVK into the bottle (native DLL overrides, builtin originals kept in dll-backup-builtin/) and trimmed the expensive LFS settings (AA off, mirror AA off, shadow cascades 4->2, dynamic reflect 8 4 -> 2 1, external mirror off). Result measured with the DXVK overlay: 100 fps with an 8.5-11.5 ms frame-time spread, versus 58 fps with heavy spikes before. `LFS_HUD=1 scripts/play-lfs.sh` shows the overlay on demand.

## [2026-09-02] diag | Steam's "not responding" traced to CEF — RaceRoom is blocked on Wine, not on a login

Wine 7.7 against Chrome 126 is the ceiling. Incidentally applied the client update that had sat downloaded-but-uninstalled since 02:49 — the bottle is now on 1788291500 — and confirmed the WPAD manifest stall is still there but cosmetic, 120 s then `http error 0` then Steam carries on.

## [2026-09-03] milestone | RaceRoom installed under Wine 11 — three sims on disk, force feedback outstanding on the third
The 74.6 GiB download completed at 00:51: `StateFlags 4`, `SizeOnDisk 79914942897`, `Game/RRRE64.exe` on disk, staging directory emptied, 28 GiB free. Took roughly 2h40m; throughput opened at 156 Mbps, sagged to 21 Mbps around the 60% mark, then recovered. One thing worth remembering for any future progress reporting: `appmanifest_*.acf` is flushed only periodically, so its `BytesDownloaded` field is stale and reads as ~0% for long stretches while the download is in fact running at full speed. The live figures come from `SteamClient.Downloads.RegisterForDownloadOverview`, which is callback-only — there is no getter — so register a handler that stashes the overview on `window` and read it back on the next evaluate. `StateFlags` in the same manifest *is* written on state transitions, so it remains a reliable completion signal even though the byte counters are not.

## [2026-09-03] blocked | RaceRoom launches but cannot compile its DX9 postprocessing effect
The game installs, launches, satisfies Steam DRM and reaches MoltenVK, then stops on a modal: `Failed to compile effect '…\shaders\dx9\fx\postprocessing.fx'`. `.fx` files are D3DX9 effects validated against the D3D9 device's caps at runtime. Neither obvious fix works. Installing Microsoft's real d3dx9 via `winetricks -q d3dx9` changes nothing — so this is not Wine's d3dx9 being incomplete. And DXVK's D3D9 cannot start on MoltenVK at all: RaceRoom's own bundled `Game/x64dxvk/` build, DXVK 1.10.3 and DXVK 3.1 all fail (`DxvkAdapter: Failed to create device`, or `No adapters found` on 3.x), even though DXVK's d3d11 works fine on the same machine — so there is no escape from wined3d for D3D9 here. The `-steam -dx11` launch option does not dodge it either. Prefix left clean: d3d9 reverted to builtin, d3dx9 left native (harmless), d3d11/dxgi/d3d10core still DXVK. Full write-up with the three untried ideas in [[raceroom-dx9-effect-compile-fails]]. Method lesson worth keeping: the failure is a Win32 message box that writes nothing to stderr, so grepping the log for "failed to compile" returns zero and reads as success — it was reported fixed twice on that basis. Process CPU is the honest proxy: rendering holds >5%, blocked-on-modal sits at exactly 0.0.

## [2026-09-03] blocked | RaceRoom runs under Wine 11 but crashes during load; shim hardened for Wine 11 along the way
Two real fixes landed. The DX9 shader wall is gone for good: Wine's `ID3DXEffectCompiler` is a stub, and **both** `d3dx9_43` and `d3dcompiler_43` must be native — d3dx9 alone is not enough because it delegates the compile. And the shim gained three symbols, because Wine 11's winebus resolves 55 where wine-7.7 resolved 52; the missing `SDL_HapticNumAxes`, `SDL_HapticSetAutocenter` and `SDL_JoystickGetSerial` came back NULL and were called anyway. The G29 also reports no serial, so `SDL_JoystickGetSerial` returns NULL and now yields "" instead. Makefile assertion moved 52 -> 55 so a future gap fails the build rather than crashing a game.
The game is still not playable: it dies during loading at `rrre64+0xc1ddad`, a null read on a worker thread, **identically in every configuration** — with the shim, without the shim, SDL backend on, SDL backend off, `DisableInput` set, and with the wheel physically unplugged. None of our stack is implicated; see [[raceroom-crashes-during-load]] for the full elimination table so it is not re-run.
Process lesson worth more than the fixes: three separate "it's fixed" calls were wrong, each from an observation window shorter than the ~3-minute failure, or from grepping a log for a failure that only ever appears as a GUI message box. For this class of bug the only valid evidence is a run longer than the failure time plus the user's screen — and a crash address that stays identical across changes is itself the signal that the thing just changed is not the cause.

## [2026-09-03] finding | RaceRoom is anti-debug protected, which rules out winedbg and invalidates how every crash test was launched
Attaching `winedbg` to RaceRoom gets a flat refusal from the game — "The application cannot run under a debugger. Deactivate all active debugging and run the application again." It ships `Game/protect.exe` and `Game/protect.dll`. So live debugging is unavailable and the saved `backtrace-*.txt` dumps are the only fault detail there will be. More importantly, the protection profile fits the load-time crash better than anything else tried: a background thread off `BaseThreadInitThunk`, firing at irregular one-to-four-minute intervals, at one constant address, indifferent to graphics, input backend, the shim, and whether the wheel is plugged in — that is the shape of a periodic integrity check, not a renderer or input fault. And it exposes a flaw in the whole night's method: every test launched `RRRE64.exe` directly with `SteamAppId`/`SteamGameId` faked in the environment, which is not how a protected Steam title expects to start. The elimination table in [[raceroom-crashes-during-load]] should be re-run under a real Steam launch (`scripts/steam-wine11.sh play`) before any of it is trusted.

## [2026-09-03] fix | Launching RaceRoom made reliable — scripts/play-raceroom.sh
Starting the game by hand was a coin flip, and the reason had nothing to do with the load crash. Steam blocks the launch behind two modals that are invisible on a black window: the once-per-session "Grab a controller", and — after any crash — "Cloud Out of Date" ("that save is not yet in the cloud"), which renders inside the main Steam window rather than as a separate `Steam Dialog` target and has "Cancel" sitting right beside "Play anyway", so buttons must be matched by text rather than taken first. Before that dialog is even created the launch parks on `SynchronizingCloud`/`pendingcloudsessions` with `bWaitingForUI:false` while `GetCloudPendingRemoteOperations` reports nothing pending; `ContinueGameAction(id)` is the nudge that creates the dialog. A launch that never completes also wedges a `LaunchApp` action that blocks the next one. All of it is now handled by `scripts/play-raceroom.sh`, along with waiting for the client UI to genuinely mount (count Supernav CEF targets, not just a live DevTools port) and restarting a spinner-stuck client once. Added `scripts/steam-cdp.py`, a stdlib-only DevTools client, which the launcher and any future black-window work both need.
